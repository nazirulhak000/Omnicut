# แผน: ปุ่มเดียว ผลิต → เรนเดอร์ (ไม่จัดคิวโพสต์)

- วันที่: 2026-11-12 · ดำเนินการโดย: Claude Code (Claude Opus 5.5)
- สถานะ: **เจ้าของตัดสิน D1–D4 แล้ว (2026-11-12)** รอสั่งลงมือ ยังไม่แตะโค้ด
- ต่อจาก: [ONE_CLICK_FLOW_PLAN_20261112.md](ONE_CLICK_FLOW_PLAN_20261112.md) (B1 สองปุ่ม) — ข้อนี้คือทาง B2 เดิม แต่ตัดขั้นคิวโพสต์ออก

## 1. ที่มา

- เจ้าของกด `ผลิตถึงดราฟต์` แล้วกด `เรนเดอร์และเข้าคิว` ต่อทันทีกับสินค้าจริง 6 คลิป เสร็จไม่ถึง 2 นาที ไม่ได้แก้ดราฟต์คั่นกลาง
- เจ้าของทำงานแบบ **เรนเดอร์ทุกคลิปให้ครบก่อน แล้วค่อยจัดคิวทีหลัง** จึงไม่ต้องการให้ระบบเปิดหน้าตารางโพสต์หลังเรนเดอร์

## 2. ระบบตอนนี้ (อ่านจากโค้ด)

| ปุ่ม | ฝั่ง server (`scripts/production_chain.py`) | ฝั่งหน้าเว็บ (`ProductToClip.jsx`, `lib/productionChain.js`) |
| --- | --- | --- |
| `ผลิตถึงดราฟต์ (N)` | `run_draft_chain`: เสียงทุกมุมที่มีบทและยังไม่มีดราฟต์ → สแกนฉาก → สร้างดราฟต์ → หยุด | ข้อความยืนยันบอกว่าหยุดให้ตรวจใน Editor |
| `เรนเดอร์และเข้าคิว (N)` | `run_render_chain`: เรนเดอร์ทุกดราฟต์ `in_production` จากค่าที่บันทึกไว้ ทีละไม่เกิน `render_concurrency()` งาน; หลังเรนเดอร์แต่ละคลิป ปก + ความคมชัด TikTok ทำงานเอง | เมื่อจบและได้คลิป ≥ 1 → `chainFollowUp().openSchedule` → ไปหน้า Tracker และเปิดพรีวิวจัดคิวอัตโนมัติ (`requestScheduleAutofill`) |

- "เข้าคิว" **ไม่ได้อยู่ฝั่ง server** เป็นแค่หน้าเว็บเปิดตารางโพสต์ให้ตอนจบ ไม่มีการเขียนคิวเอง
- งานเบื้องหลังสินค้าละ 1 งาน (กดซ้อนได้ 409) วิ่งต่อแม้ปิดหน้าเว็บ กดใหม่หลัง restart แล้วข้ามขั้นที่เสร็จแล้ว

## 3. ข้อเสนอ

1. **Server:** เพิ่มชนิดงานที่ 3 `full` ใน `production_chain.py`
   - `run_full_chain` = เรียก `run_draft_chain` แล้วต่อ `run_render_chain` ในงานเบื้องหลังตัวเดียว (ใช้ฟังก์ชันเดิมทั้งคู่ ไม่เขียนขั้นใหม่)
   - หยุดก่อนเรนเดอร์เมื่อ: ยกเลิก · สแกนฉากล้ม (กฎเดิมของ B1) · ไม่มีมุมไหนได้เสียงเลย
   - ดราฟต์ล้มบางมุม → เรนเดอร์มุมที่ได้ดราฟต์ แล้วรายงานมุมที่ล้ม (D4)
   - เรนเดอร์**เฉพาะมุมที่สร้างดราฟต์ในรอบนี้** (D3) — `plan_render` รับชุด angle ที่อนุญาต ดราฟต์ที่ค้างจากก่อนหน้าไม่แตะ
   - progress: ขั้นดราฟต์ 0–50%, ขั้นเรนเดอร์ 50–100% (ขั้นเรนเดอร์เดิมรายงาน 0–100% ของตัวเอง ต้องแบ่งช่วง)
   - ผลรวม `{kind: "full", draft: {...}, render: {...}, message}` ข้อความเช่น `สร้างดราฟต์ 6 มุม · เรนเดอร์เสร็จ 6 คลิป`
2. **หน้าเว็บ:** เพิ่มปุ่มที่ 3 `ผลิตจนเรนเดอร์เสร็จ (N)` (D1) — N = มุมที่มีบทและยังไม่มีดราฟต์ (เท่าปุ่ม `ผลิตถึงดราฟต์`, D3)
   - ปุ่มเดิม `เรนเดอร์และเข้าคิว` → `เรนเดอร์ดราฟต์` จบแล้ว **ไม่เปิดตารางโพสต์** เช่นกัน (D2) · ถอด `requestScheduleAutofill` ออกจาก flow ของ chain (ตัว `consumeScheduleAutofill` ในตารางโพสต์ยังอยู่ ไม่มีใครตั้งค่าแล้ว)
   - จบแล้วแสดง toast + รีเฟรชรายการมุม **ไม่เปิดตารางโพสต์**
   - ข้อความยืนยันบอกชัดว่าไม่หยุดให้ตรวจดราฟต์
3. ไม่แตะ: ขั้นเสียง / สแกน / ดราฟต์ / เรนเดอร์ / ปก / ความคมชัด (ใช้ของเดิมทั้งหมด) · ไม่แตะตารางโพสต์ · ไม่แตะฟอนต์และข้อความในคลิป

## 5. ข้อจำกัด / ความเสี่ยง

- ไม่มีจุดตรวจดราฟต์ก่อนเรนเดอร์ — ดราฟต์ที่ผิด (เลือกฉากไม่ตรง) จะออกเป็นคลิปเลย ต้องเรนเดอร์ซ้ำจาก Editor
- ดราฟต์ที่ใช้ Cutout เฉพาะช่วงข้อความถูกข้าม (กฎเดิม ต้องเรนเดอร์จาก Editor) — บอกในผลสรุป
- งานสะดุดระหว่างเรนเดอร์ (restart / ยกเลิก): กดปุ่มใหม่ซ้ำ **จะไม่เรนเดอร์ดราฟต์ที่สร้างไปแล้ว** เพราะ D3 นับเป็นดราฟต์เก่า → ใช้ปุ่ม `เรนเดอร์ดราฟต์` เก็บส่วนที่ค้าง (บอกในข้อความผลสรุปเมื่อจบไม่ครบ)
- **ชนไฟล์:** ตอนเขียนแผน Antigravity กำลังแก้ `ProductToClip.jsx` (รอบ `ANTIGRAVITY-REMOVE-AI-COPILOT-BUTTON-20261112`) — ลงมือหลังเขาเสร็จ หรือแก้เฉพาะช่วงปุ่ม chain
