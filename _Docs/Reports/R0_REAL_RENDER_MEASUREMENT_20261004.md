## A. A6 reverse J-cut: ตัดตรงทุกรอยต่อ (วัดจากไฟล์ผลลัพธ์)

lead = เวลาที่ภาพเปลี่ยน − เวลาที่เสียงเริ่ม (ค่าบวก = เสียงมาก่อนภาพ = J-cut, มาตรฐาน 150–250 ms)

| first_cue_start | รอยต่อ | ภาพเปลี่ยน (s) | เสียงเริ่ม (s) | lead (ms) | lead (เฟรม) |
|---|---|---|---|---|---|
| 0.0 | 1 / 2 / 3 | 2.200 / 4.200 / 6.200 | 2.000 / 4.000 / 6.000 | +200 / +200 / +200 | +6 |
| 0.1 | 1 / 2 / 3 | 2.200 / 4.200 / 6.200 | 2.100 / 4.100 / 6.100 | +100 / +100 / +100 | +3 |
| 0.3 | 1 / 2 / 3 | 2.200 / 4.200 / 6.200 | 2.300 / 4.300 / 6.300 | **−100 / −100 / −100** | **−3** |

- ยืนยันกลไกของ A6 ด้วยการเรนเดอร์จริง: rendered lead = 0.2 − fcs **ภาพเปลี่ยนก่อนเสียงเมื่อ fcs > 0.2 s**
  (R1 คำนวณจาก clip list ได้ 0.18 − fcs ส่วนที่ต่างไป +1 เฟรมมาจาก B5 ดูข้อ B(c))
- **ที่ t=0:** เฟรม 0 เป็นเฟรมดิบ #24 ซึ่งคือ trim_start 0.8 ของ shot 0 ในทุกค่า fcs ช่วงที่เสียงยังเงียบอยู่จึงมีภาพตั้งแต่ต้น ไม่มีจอดำหรือจอว่างที่หัว
  ส่วน "silent gap" ที่ comment ใน `shot_matching_stage.py:595-602` พูดถึง **ไม่ได้เกิดที่หัวไฟล์** สิ่งที่เกิดจริงคือ clip รวมกันได้สั้นกว่าเสียง fcs วินาที
  แล้ว `video_editor.py` ใช้ `tpad=stop_mode=clone` ค้าง**เฟรมสุดท้าย**ไว้ 0 / 3 / 9 เฟรม (fcs 0 / 0.1 / 0.3)
- ความยาว: สตรีมภาพ 8.000 / 8.100 / 8.300 s เท่ากับความยาวเสียง · สตรีมเสียง AAC 8.000 / 8.107 / 8.320 s (ส่วนเกินคือ padding ของ encoder)

### ตัวแปร B: transition ที่ VideoAssemblyStage จะใส่จริง (วัดเพื่อประกอบเท่านั้น ไม่มีในเทส)

แผนจาก ShotMatchingStage เป็น `cut` ทั้งหมด (โดน style budget) แล้ว VideoAssemblyStage ก็เปลี่ยนเป็น `circleclose/circleopen/circleclose` ยาว 0.35 s
พร้อมยืด clip ละ +0.35 s (ประเด็น A7) xfade จึงเริ่มที่จุดตัดเดิมแล้วจบช้ากว่านั้น 0.35 s
วัดจากสัดส่วนพิกเซลของช็อตใหม่ที่กริด 18x32 ค่าที่ได้ (เริ่ม / ครึ่ง / ครบ) ตรงกันทุก fcs:
`2.333/2.367/2.433`, `4.367/4.400/4.433`, `6.333/6.367/6.433`
lead ที่จุดครึ่งเทียบกับเสียงคือ fcs 0.0 → +367/+400/+367 ms · fcs 0.1 → +267/+300/+267 · fcs 0.3 → +67/+100/+67
สรุปว่าใน pipeline จริง xfade ทำให้ภาพมาช้ากว่ากรอบ 250 ms ไปมาก (เรื่องของ A7) แต่ fcs ก็ยังกินค่า lead ออกไปเท่ากับตัวมันเองเหมือนเดิม
(circle wipe เริ่มเปลี่ยนจากขอบภาพ ส่วนกลางภาพเปลี่ยนช้ากว่านี้อีก)

## B. ตรวจผลของ R1 บนเฟรมจริง

**(a) split คลิปที่มี zoom ramp:** ใช้ `splitClipAt` ตัวจริงผ่าน node (ไฟล์ timelineMath.js ปัจจุบัน ซึ่งเลน E1 กำลังแก้ส่วน easing อยู่)
คลิป zoom 1.0→2.0 ใน 2 s ตัดที่ 1.0 s ได้ left `[0:1.0, 1:1.5]` และ right `[0:1.5, 1:2.0]` แล้วเรนเดอร์ต่อกันเทียบกับคลิปที่ไม่ได้ split
- ผลต่างเฉลี่ยต่อพิกเซลระหว่าง split กับ unsplit (สเกล 0–255, กริด 90x160): เฟรม 0–27 ได้ 0.00 · เฟรม 28–59 ได้ ≤ 1.0
  ยกเว้น 2 เฟรมที่เป็น outlier ของ x264 (เฟรม 35 = 6.1, เฟรม 50 = 5.55 ไม่ได้อยู่ที่รอยต่อ) · ที่รอยต่อเฟรม 29/30 ได้ 0.02/0.08
- ความต่างระหว่างเฟรมติดกันตรงรอยต่อ: split 28.47 เทียบกับ unsplit 28.49 (ระยะซูมปกติของ 1 เฟรม)
  ถ้าคัดลอก keyframe เดิมไปทั้งสองฝั่งแบบก่อน R1 (สร้างเป็นข้อมูลเทสอย่างเดียว ไม่ได้ย้อนโค้ด) ได้ **79.8** คือภาพกระโดดชัดเจน → **ผ่าน**
- ข้อสังเกต: `splitClipAt` ยังคงค่า `duration` ของคลิปแม่ (2) ไว้ในทั้งสองฝั่ง เทสนี้ตั้ง duration ใหม่จาก trim
  ยังไม่ได้ตรวจว่า video_editor อ่าน `duration` ที่ค้างอยู่นี้หรือไม่

**(b) Ken Burns:** ใช้ `ImageMotionEngine.generate_motion_video_from_images` ตัวจริงกับภาพแนวนอน 1600x900 และแนวตั้ง 900x1600 ที่มีวงกลมดำรัศมี 250 px
- segment ได้ 48 และ 45 เฟรม = ceil(1.6·30) และ ceil(1.5·30) พอดี · ไฟล์รวมได้ 93 เฟรม · ทุกไฟล์ขนาด 1080x1920
- กรอบของวงกลม (w×h) ที่เฟรม 0 / 47 / 48 / 92 ได้ 300×300, 344×344, 461×460, 403×403 อัตราส่วน 1.00 ไม่ถูกยืด
  (ถ้ายืดเป็น 3:4 แบบเดิม ภาพแนวนอนจะได้ ~0.42) · เรนเดอร์ใช้เวลา ~1.3–2.2 s → **ผ่าน**

**(c) จุดตัดอยู่บนกริด 1/30:** PTS ของทุกจุดที่ภาพเปลี่ยนในทั้ง 3 เรนเดอร์คือ 2.2 / 4.2 / 6.2 เป็นพหุคูณของ 1/30 คลาดไม่เกิน 1 ms
จุดตัดตามแผน (ผลรวม duration) คือ 2.167 / 4.167 / 6.167 ก็อยู่บนกริดเช่นกัน → **ผ่าน**
แต่เรนเดอร์ช้ากว่าแผน **+1 เฟรม (33 ms)** ทุกจุด เพราะ clip แรกเก็บ trim 0.8–2.967 (2.167 s = 65.01 เฟรม) แล้ว ffmpeg ปัดขึ้นเป็น 66 เฟรม
นี่คือ B5 ที่เป็นงานของเลน TM เทสตอนนี้ยอมให้คลาด ≤ 1 เฟรม
